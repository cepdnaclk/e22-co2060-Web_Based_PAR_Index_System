# Security Review — Web-Based PAR Index System

This review covers only what was actually inspected in source code and
confirmed with actual test output. Where a claim is backed by a test, the
test name is given so it can be re-run and re-verified independently. Nothing
here is asserted from assumption.

Backend test baseline referenced throughout: **107/107 passing — 0 failures —
0 errors — BUILD SUCCESS** (see `mvn test` output; not a coverage measurement).

---

## 1. Authentication — JWT issuance and validation

### 1.1 Token issuance (`JwtUtil.generateToken`)

Tokens are signed HMAC-SHA (`Keys.hmacShaKeyFor`) with a key derived from a
configured secret (`app.jwt.secret`, base64-decoded, minimum 32 bytes
enforced at startup via `JwtUtil.validateSecret()`). Claims include the
subject (user's email/username) and a `roles` claim listing granted
authorities. Expiration is configurable (`app.jwt.expiration-ms`).

### 1.2 Token validation (`JwtUtil.isValid`, `JwtAuthFilter`)

`JwtAuthFilter` reads the `Authorization: Bearer <token>` header, extracts the
username, loads the corresponding `UserDetails`, and accepts the token only if
the subject matches and the token is not expired. Any exception during this
process (malformed token, unknown user, expired token, bad signature) is
caught and the request proceeds **unauthenticated** rather than throwing —
authorization is then enforced downstream by Spring Security's role checks,
not by this filter directly rejecting the request.

**Verified by:**
- `JwtAuthFilterTest` (5 tests) — no header, malformed header, valid token,
  invalid/rejected token, unknown user — all confirm the filter's decision to
  authenticate or not, and confirm the filter never itself blocks the request
  (`chain.doFilter` is always called).
- `JwtRoundTripIntegrationTest` (3 tests) — uses the **real** `JwtUtil` and
  **real** `JwtAuthFilter` together (no mocking of either), and confirms:
  - a token generated by the real `JwtUtil` is correctly accepted by the real
    filter, with the correct username and role authority attached to the
    resulting `SecurityContext`;
  - a genuinely expired token (real expiration check, not a mocked boolean) is
    correctly rejected;
  - a token signed with a **different** secret than the one the filter's
    `JwtUtil` is configured with is correctly rejected.

  This closes a gap that existed before this review: `AuthServiceTest` and
  `JwtAuthFilterTest` each test their own class correctly but mock the other
  side, so neither alone proves the two actually agree on token format, claim
  names, or signing key end to end.

### 1.3 Confirmed defect: hardcoded JWT secret fallback

See `BugLog.md`, **BUG-001**. Summary: `application.yml` supplies a fallback
JWT secret if `JWT_SECRET` is not set in the environment. The fallback value
is committed to the public repository. This does not indicate the
signature-checking mechanism is broken (§1.2's forged-token test confirms
that mechanism works correctly) — the defect is that the fallback key itself
is known, so any deployment that omits `JWT_SECRET` is signing tokens with a
publicly visible key. **Not yet fixed** — deferred pending a deliberate,
reviewed change, since removing the fallback changes deployment startup
behavior.

## 2. Authorization

### 2.1 URL-level role restrictions (`SecurityConfig`)

`/api/v1/cases/**`, `/api/v1/patients/**`, `/api/v1/training-sets/**`, and
`/api/v1/admin/**` each have URL-pattern-based role restrictions in
`SecurityConfig`, layered on top of method-level `@PreAuthorize` annotations
on individual controller methods.

**Note:** `MLController.getAuditLogs()` is mapped to
`/api/v1/ml/admin/audit-logs` (not `/api/v1/admin/audit-logs`, as its own
Javadoc states) — so `SecurityConfig`'s `/api/v1/admin/**` URL-level rule does
not actually cover this endpoint. It falls through to `anyRequest().authenticated()`,
and ADMIN-only enforcement here relies entirely on the method-level
`@PreAuthorize("hasRole('ADMIN')")`. This was confirmed by inspection; method
security is active (`@EnableMethodSecurity`), so this is not a functional gap,
only a documentation/consistency inconsistency worth correcting.

### 2.2 Controller-level authorization checks

**`FileServeController`** — `@PreAuthorize("hasAnyRole('ORTHODONTIST','ADMIN')")`
restricts the endpoint at the role level; `AccessControlService.requireModelReadable`
then enforces per-file ownership/case-access at the service level.

**Verified by:** `FileServeControllerSecurityTest` (3 tests) — confirms an
unauthorized role is blocked before the repository/service layer runs at all,
confirms a role-permitted-but-not-file-permitted request is rejected via the
service-layer check, and confirms a fully authorized request succeeds.

*(Note: these three tests initially failed for an unrelated reason — a
`@MockBean` of `JwtAuthFilter` silently swallowed every request instead of
forwarding it down the filter chain, since a bare Mockito mock of a filter is
a no-op. This was a test-configuration bug, not a production defect; see
commit history / prior session notes for the fix, which stubs the mock to
call `chain.doFilter(...)`.)*

**`CaseController`** — `finalize()`/`unfinalize()` enforce business-rule
preconditions (a case cannot be finalized without a calculated, non-zero PAR
score; cannot be unfinalized without a reason; state transitions are guarded
against re-finalizing an already-finalized case or unfinalizing a
not-currently-finalized one).

**Verified by:** `CaseControllerTest` (8 tests) covering the success path and
every precondition-violation branch, with HTTP status codes confirmed against
the actual `GlobalExceptionHandler` mapping (`IllegalArgumentException` → 400,
`IllegalStateException` containing "already finalised"/"not currently
finalised" → 409, other `IllegalStateException` → 422).

**`TrainingSetController`** — `review()` restricts approval to the assigned
reviewer or an admin, and enforces a `groundTruthPar` range (1–50) and
completeness of uploaded model files (all three slots present) — but only
when the review outcome is `APPROVED`; a `REJECTED` review is not subject to
these checks.

**Verified by:** `TrainingSetControllerTest` (6 tests), including a test that
specifically confirms the APPROVED-only scoping of these checks (a REJECTED
review with an otherwise-invalid submission still succeeds, and never queries
the model-file repository).

**Flagged, not yet resolved:** `delete()` on the same controller has no
ownership check — see `BugLog.md`, **FLAGGED-001**.

**`MLController`** — role restrictions differ meaningfully by endpoint:
`ORTHODONTIST` is permitted on `/status` but excluded from `/metrics` and
`/train`; `/rollback` and `/admin/audit-logs` are ADMIN-only.

**Verified by:** `MLControllerTest` (9 tests), deliberately testing both the
"blocked" and "allowed" case for the `/metrics` and `/train` endpoints
specifically, since a role restriction that differs between visually similar
endpoints is exactly the kind of thing a copy-pasted `@PreAuthorize`
annotation can silently break in either direction.

## 3. File storage and path traversal protection

`StorageService.resolveReadablePath` (used by both `FileServeController` and
`TrainingSetController`) guards against path traversal by resolving the
requested relative path against a fixed base directory and verifying the
result still starts with that base path.

**Verified by:** `StorageServiceTest` (8 tests total), including:
- `resolveReadablePathRejectsTraversal` — a `../../etc/passwd`-style path is
  rejected with `SecurityException`.
- `deleteRefusesTraversalPaths` (pre-existing) — confirms `delete()` silently
  refuses a traversal path rather than deleting outside the base directory.
- Null/blank path rejection, and a legitimate relative path resolving
  correctly within the base directory.

**Confirmed gap (not a traversal issue):** file **content-type** validation
is incomplete — see `BugLog.md`, **BUG-002**. `ALLOWED_MIMES` is declared but
never checked; only the file extension is validated. This does not weaken the
path-traversal protection above, which is independent of file-type checking.

Upload validation (`StorageService.validate`) also rejects empty files and
files over the 50 MB limit — confirmed by
`storeClinicalRejectsEmptyFile`/`storeClinicalRejectsOversizedFile`.

## 4. Areas not yet covered by this review

- **ML-service-to-backend communication** (`MLClientService`,
  `MlPredictionService`) — the `X-ML-Service-Key` header mechanism was
  observed during the stray-file investigation (see `BugLog.md`,
  RESOLVED-001) but has not been independently security-reviewed for secret
  handling or transport security.
- **Docker/deployment configuration** beyond the JWT secret fallback itself.
- **Landmark controller endpoints** (`LandmarkController`) — the underlying
  `GeometricPARService` is well-tested (15/15 in `GeometricPARServiceTest`),
  but the controller's own authorization/validation behavior has not been
  separately tested or reviewed.

These are noted as open scope, not assessed as safe or unsafe.
